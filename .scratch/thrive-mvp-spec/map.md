# Map: Thrive MVP Engineering Specification

## Destination

A build-ready **THRIVE MVP — Engineering Specification v1.0**: screen-by-screen behavior, navigation map, database schema, API contracts, RLS/permission rules, the financial transaction model, validation rules, error states and acceptance criteria — for a universal Expo (React Native + Expo Router, targeting iOS/Android/Web) app backed by Supabase, covering **one complete community-finance cycle** (join → membership → contribution → loan request → Loan Review Panel approval → disbursement → repayment → report) for a single pilot group. This map produces the spec only — no application code is written as part of it (see [[../../CONTEXT.md]] for the domain glossary this spec is written against).

## Notes

- Domain: fintech / community-savings mobile+web app. See `../../CONTEXT.md` (project root) for the glossary — consult and update it whenever a schema or workflow ticket sharpens a term.
- Call the `domain-modeling` skill whenever a ticket touches the data model or workflow terminology.
- Call the `codebase-design` skill when a ticket shapes an API/module interface (e.g. the API-contract-shape ticket).
- Standing principle: financial truth is the Transaction ledger; balances are always derived, never stored (see resolved ticket 03).
- Standing principle (ticket 19): don't create a database object because a screen exists for it — create one only when there's a persistent fact that must be stored. Reports, the Admin's Actions Required queue, and "My Records" all stayed screens with no backing table for exactly this reason.
- Build execution (once this spec is done) is a separate future effort: AI-assisted (Claude Code) with the user as product owner; a human specialist reviews before anything touching real money movement, payment integration, or production security/compliance ships.
- Recommended build order for that future effort, for reference: vertical slices — Identity → Group → Money → Loans → Governance → Reporting. Not binding on this map, but the spec should be organized so it can be executed that way.

## Decisions so far

- [Scope & build philosophy](issues/01-scope-and-build-philosophy.md): Destination is a Layer-1 MVP spec for one complete group financial cycle (not every mockup screen); trimmed to ~32 screens across 9 sections; user is product owner, AI-assisted build now, human specialists gated in before real money movement/production security.
- [Tech stack & distribution](issues/02-tech-stack-and-distribution.md): Expo + React Native + TypeScript + Expo Router (universal iOS/Android/Web) + Supabase (Postgres, Auth, RLS, Edge Functions, Storage); web ships as an installable PWA now, native app-store builds via EAS later.
- [Financial ledger & payment model](issues/03-financial-ledger-and-payment-model.md): Event-sourced Transaction ledger, balances always derived, never stored; no live payment-gateway integration in V1 — record-and-verify only.
- [V1 roles & permissions](issues/04-v1-roles-and-permissions.md): Member, Group Admin, System Admin. Treasurer folded into Group Admin until usage proves a need to split it out.
- [Loan approval mechanism](issues/05-loan-approval-mechanism.md): Auto-selected 3-member "Three-Eye" Loan Review Panel (reputation = ≥1 completed loan, zero defaults), 2-of-3 fail-fast approval, falls back to Group Admin if fewer than 3 eligible members exist. *(Revised from an original 5-member/3-of-5 design during ticket 10's grilling — the mockup's screens are explicitly branded "Three-Eye Approval.")*
- [Scope boundaries: offline, multi-group, identity](issues/06-scope-boundaries-offline-multigroup-identity.md): Offline-first sync deferred; multi-group membership modeled in schema but only single-group flow built/tested for the pilot; identity is phone + profile only, no KYC/document upload in V1.
- [Auth mechanism feasibility](issues/07-auth-mechanism-feasibility.md): Phone+OTP flow is natively supported via Supabase Auth's `signInWithOtp`/`verifyOtp` (SMS provider: Twilio to start; billed per-message by the provider, not Supabase); the "Thrive PIN"/Face ID re-entry step is not a Supabase feature at all — it's a fully local `AppLockGate` (expo-local-authentication for biometrics, a locally-hashed PIN via expo-secure-store/expo-crypto) layered in front of a Supabase session persisted with the `LargeSecureStore` pattern (expo-secure-store + AsyncStorage + aes-js), native-only (no Face ID/SecureStore on web).
- [Core identity & group schema](issues/08-core-identity-and-group-schema.md): `profiles` (1:1 with `auth.users`, `is_system_admin` as a global flag), `groups` (System-Admin-created only in V1, no self-serve create-group flow), `memberships` (many-to-many join, `status: pending→active/declined/exited` models the apply/review flow on one row, membership *admission* deferred to a Governance vote per ticket 11 — refined there to allow a Group Admin unilateral-reject path — bootstrap exception for a new Group's first admin/seed members). Reputation and PIN are both deliberately absent from the schema — derived/local respectively, never stored columns.
- [Financial ledger schema](issues/09-financial-ledger-schema.md): single append-only `transactions` table (signed `amount`, open `type` TEXT not a Postgres enum, `status: posted→reconciled/investigate`) covers Contribution/Loan Disbursement/Repayment/Reversal; Shares confirmed in V1 scope (`share_value` on `groups`, contribution must be an exact multiple, `shares_earned` stored on the row); a lightweight `reconciliation_cases` table is the actual verification mechanism (bulk, after-the-fact, never gates posting); mistakes are fixed only via compensating reversal rows, never edit/delete. End-of-year Share Valuation & Profit Distribution deferred to Layer 2 (see Out of scope).
- [Loan & repayment schema](issues/10-loan-and-repayment-schema.md): `loans` (state machine driven by the ledger: disbursed/repaying/repaid derived from `transactions`, never set by hand), `loan_reviewers` (one row per Three-Eye panelist, fail-fast 2-of-3 resolution, random selection excluding borrower + conflict-of-interest), `loan_clarification_requests` (non-blocking, doesn't count as a vote). Zero-interest/zero-fee in V1. No reviewer timeout and no automated default detection — both manual/Group-Admin-driven, deliberately, to avoid scheduler/cron complexity in Layer 1. Repayments are plain `transactions` rows, no separate table. Revises [loan approval mechanism](issues/05-loan-approval-mechanism.md)'s panel size (5→3) and threshold (3-of-5→2-of-3) to match the mockup's actual "Three-Eye" branding.
- [Governance schema](issues/11-governance-schema.md): `motions` (open TEXT `type`, V1 only builds `membership_application`) + `votes` (`voter_id`+`choice` both stored — confidential from peers via RLS in ticket 12, not anonymous to the system, for audit/fraud-detection). No quorum in V1, simple majority of votes cast, hardcoded 7-day window stored explicitly per-Motion. Refines [core identity & group schema](issues/08-core-identity-and-group-schema.md): a Group Admin may pre-screen and reject an application outright (no Motion), but can never admit a member unilaterally — only a passed vote can.
- [RLS policy design](issues/12-rls-policy-design.md): RLS is read-access control only — every write goes through service-role Edge Functions (ticket 13), so almost no table has a client-facing INSERT/UPDATE/DELETE policy. Radical within-group financial transparency: any active member reads every `transactions`/`loans` row in their group, not just their own (`reconciliation_cases` stays Admin-only). Secret ballot holds even against the Group Admin (`votes` SELECT is strictly own-row; aggregates via a definer-owned `motion_tallies` view). New decision: Three-Eye reviewer identity is hidden from the borrower/other members even after resolution (`loan_reviewers`/`loan_clarification_requests` restricted; anonymized `loan_review_progress`/`loan_clarification_messages` views carry the substance without identity). Full policies in [rls-policies.sql](rls-policies.sql).
- [API contract shape](issues/13-api-contract-shape.md): the concrete Edge Function/RPC list (17 operations across membership, loans, and the ledger) plus the four items ticket 12 flagged: Motions resolve via a `pg_cron` sweep + inline fail-fast on each vote (extended from the Three-Eye panel to membership voting too — flagged as an inference, not a clean restatement); borrower "Eligible Amount" = `total_contributed × 3`, a plain view, no new group setting; `audit_events` added (narrow scope — discretionary/corrective actions only, not routine events); loan disbursement is a separate explicit Admin action, atomic with the ledger write. This closes out the map — every ticket 01–13 is now resolved.

## Database blueprint

[database-blueprint.sql](database-blueprint.sql) consolidates tickets 08–11 (plus `audit_events`/`loan_eligibility` from ticket 13) into one build-ready DDL file — tables, CHECK constraints in place of enums, derived-value views, baseline indexes. [rls-policies.sql](rls-policies.sql) (ticket 12, extended by ticket 13) attaches every access-control policy and the anonymized/aggregate views (`profiles_public`, `motion_tallies`, `loan_review_progress`, `loan_clarification_messages`) those policies required. Ticket 13's own file has the full Edge Function/RPC list — the write side isn't expressed as SQL DDL the way reads are, so it lives there rather than in a third consolidated file.

## Screen-by-screen behavioral spec (phase 2)

Tickets 01–13 produced the backend (schema/RLS/API). This phase covers the ~32 screens across 9 sections ticket 01 scoped, grouped into 6 tickets along the same vertical-slice order as the recommended build order (Identity → Group → Money → Loans → Governance → Reporting):

- [14 — Identity & Access screens](issues/14-identity-access-screens.md): Splash/Welcome/Create Account/Verify Phone/Create PIN, Profile/Settings/Security. **Resolved.** No schema changes (PIN stays local-only per ticket 07). Sign In vs. Create Account are genuinely different (`shouldCreateUser` true/false); PIN is device-local so a returning account still sets a fresh PIN on a new device; sign-out wipes local secrets entirely; photo upload moved out of onboarding into Settings-only (resolves the map's open "profile photo" item below).
- [15 — Group, Home & Members screens](issues/15-group-home-members-screens.md): Home dashboard, My Groups/Group Dashboard, Join a Group (browse/apply), Member Directory. **Resolved (one item left pending — see below).** Home = personal snapshot + shortcuts; Group Dashboard = group-wide info. New backend rule surfaced here: a member may have only **one open loan at a time** per group — added to [loan schema](issues/10-loan-and-repayment-schema.md), `database-blueprint.sql` (partial unique index), and ticket 13's `requestLoan`. No "chosen by friends" social-proof (out of scope, undesigned). One mockup screen (an unclear "Membership" tile with unreadable figures) deliberately left unspecified rather than guessed at — flagged pending, no schema/nav built around it.
- [16 — Contributions screens](issues/16-contributions-screens.md): Make Contribution, Contribution Receipt, Contribution History. **Resolved.** Mobile Money only (no method selector), live client-side share-multiple validation ahead of the server check, no PDF receipt generation, Your Growth folds in as a per-period bar chart that must net out reversals against the original contribution's period (a correctness detail, not a new blueprint view).
- [17 — Loans screens](issues/17-loans-screens.md): My Loan/Eligibility, Loan Application, Under Review, Three-Eye Approval (borrower + reviewer + admin views), Loan Approved, Disbursement, Make Repayment, Loan Progress. **Resolved.** No Admin override during an active Three-Eye review — an ambiguous mockup screen deliberately not built into scope. New rules: `recordLoanRepayment` now caps at the outstanding balance (no overpayment); "Apply for Loan" disabled with any open loan; a new "Loan Declined" outcome screen shows only the aggregate reviewer count. Reviewer evidence panel is factual figures, not a reputation score (ticket 13 already ruled that out).
- [18 — Governance screens](issues/18-governance-screens.md): Vote Notification, Applicant Profile, Cast Vote, Vote Submitted, Vote Results, Membership Approved, admin Membership Review. **Resolved.** New column `memberships.application_note` (optional "reason for joining," shown to voters) — added to the blueprint, ticket 08, ticket 13. No occupation field, no contribution-history/community-involvement score for applicants (same no-invented-trust principle as ticket 17, even clearer here since an applicant isn't a member yet). No push notifications — a Governance tab replaces the mockup's notification screen. No live running tallies while a motion is open (governance-integrity, not just privacy). Fail-fast resolution enforced atomically server-side, same pattern as the loan panel.
- [19 — Reporting & Admin screens](issues/19-reporting-admin-screens.md): Admin Control Centre, Financial Dashboard, Reconciliation, Reports, Audit Log — the mockup's Administrator + Treasurer Experience rows. **Resolved.** No new schema: Reports are live/on-demand (no persistence, no export — resolves ticket 13's flagged gap), the Actions Required queue is a client-side merge of existing tables (no new "tasks" table), Audit Log is a straightforward filtered list. "My Records" resolved as out of scope (would compare a ledger against itself — not a real reconciliation), unlike ticket 15's Q4 which stays genuinely open.

**All 19 tickets are now resolved.** Ticket 15's Q4 (an unreadable mockup screen) is the spec's one deliberately-unresolved item — not inferred, left open pending a clearer source image.

## Not yet specified

- Notification design: ticket 15/18 settled that V1 has *no* push notifications at all (a Governance tab and the Home/Group screens are how members discover things instead) — so this item is really just "confirm no further notification design is needed," not open UX work.
- Pilot group onboarding/rollout mechanics (how the first real group actually gets set up on the system) — operational, not yet specified.
- How the V1 architecture should leave extension room for the deferred Layer-2+ features (see Out of scope) without building them now.
- The last-Group-Admin invariant (ticket 08) has no Edge Function enforcing it yet (ticket 13 flagged this) — no "demote/remove admin" flow exists in the mockup, so it's unbuilt rather than dropped.
- Ticket 15's Q4 — an unreadable mockup screen, deliberately left open (see above).

## Out of scope

- Analytics/insights dashboards, in-app group chat, help center, payments marketplace, advanced admin dashboards beyond the core financial dashboard, multi-language support beyond English, AI-driven/"sophisticated" notifications. These belong to later platform layers per the white paper's own Layer 2+ framing, not the Layer-1 MVP this map targets. (Captured in [Scope & build philosophy](issues/01-scope-and-build-philosophy.md).)
- End-of-year Share Valuation & Profit Distribution (the mockup's annual Valuation → Member Shares → Distribution flow). Orthogonal to the single pilot-group cycle this spec targets; the ledger's `type` column is deliberately left open (TEXT, not a closed enum) so `profit_distribution` can be added later without a redesign. (Captured in [Financial ledger schema](issues/09-financial-ledger-schema.md).)
